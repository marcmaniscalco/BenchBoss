  - **Weaker option (rejected — don't do this)**: have `template.yaml` build the `{{resolve:secretsmanager:...}}` reference itself instead of the pipeline, so it never appears in `ParameterOverrides`. Closes the CodePipeline avenue only — the resolved value still ends up in the Lambda's env var, still readable in plaintext via `lambda:GetFunctionConfiguration`/`GetFunction` to anyone with that IAM permission. No better than today on that front.
  - **Proper fix: don't put the secret in an env var at all — fetch it from Secrets Manager at runtime**, inside the Lambda code, so the actual value never appears in *any* CloudFormation/CodePipeline/Lambda console or API surface. Concretely:
    1. `infrastructure/template.yaml`: keep `DiscordPublicKey`/`DiscordToken` (lines 12-19) as-is, defaulted to `""`, for the manual path (see below). Add a new optional `DiscordSecretName` Parameter (default `""`, not NoEcho — it's just a name) and a `Condition: UseSecretsManager: !Not [!Equals [!Ref DiscordSecretName, ""]]`. On both `BenchBossFunction` and `BenchBossStreamFunction`: pass `DISCORD_SECRET_NAME` as an env var only when the condition is true (`!If [UseSecretsManager, !Ref DiscordSecretName, !Ref "AWS::NoValue"]`), and add a `Policies:` entry (also gated on the condition via `Fn::If` at the list-item level, evaluating to `!Ref "AWS::NoValue"` when false to omit it) granting `secretsmanager:GetSecretValue` scoped to `!Sub "arn:aws:secretsmanager:${AWS::Region}:${AWS::AccountId}:secret:${DiscordSecretName}-*"` — note the trailing `-*`, Secrets Manager appends a random 6-char suffix to the real ARN that CloudFormation can't predict. `Policies:` in a SAM function attaches to *that function's own* auto-created execution role, not the pipeline's deploy role — no change needed to `pipeline.yaml`'s `CloudFormationRole`.
    2. `pipeline.yaml`: change `ParameterOverrides` to pass `"DiscordSecretName": "${QaSecretName}"` (or `ProdSecretName`) instead of resolving `DiscordPublicKey`/`DiscordToken` at all.
    3. **SnapStart gotcha — this is the part that'll bite if skipped**: both functions have `SnapStart: ApplyOn: PublishedVersions` (`infrastructure/template.yaml:45,66`). SnapStart snapshots the execution environment *after* module-level init code runs and restores that frozen snapshot on future cold starts — so fetching the secret at plain module scope (like today's `DISCORD_PUBLIC_KEY = os.environ[...]` in `lambda_function.py:19-20` / `stream_lambda_handler.py:12`) would freeze whatever value existed at snapshot-creation time into *every* restored environment; rotating the secret wouldn't take effect until the next deploy, silently. Both entry points already register a `_after_restore` hook (`lambda_function.py:29-33`, `stream_lambda_handler.py:21-25`, currently just resetting `boto3.DEFAULT_SESSION`) — the secret fetch must go there instead, reassigning module globals, so it runs on every individual restore and naturally picks up rotated values (`get_secret_value` is called fresh per restore, not frozen into the snapshot).
    4. The secret's `SecretString` is a JSON object with both `DiscordPublicKey` and `DiscordToken` keys (same shape the pipelines already put there — see `bench-boss/qa`/`bench-boss/prod`, and `ParameterOverrides` in either pipeline template for the exact key names) — one `get_secret_value` call, then `json.loads(...)` and pull both keys out; no need for two separate calls or two separate secrets.
    5. Decide error handling for a failed fetch in `_after_restore` (secret deleted, permissions drift, throttling): recommend letting it raise and fail the restore/invocation loudly rather than falling back silently — a bot that can't verify Discord signatures shouldn't come up in some degraded, insecure mode.
    6. Fall back to reading `DISCORD_PUBLIC_KEY`/`DISCORD_TOKEN` directly (today's behavior, safe at module scope) when `DISCORD_SECRET_NAME` isn't set — this is what keeps `make deploy`/README Part 6 working completely unchanged, since manual deploys just never set that parameter.
    7. `local/local_server.py` needs no change — local dev already reads `DISCORD_PUBLIC_KEY`/`DISCORD_TOKEN` straight from `.env`, no Secrets Manager involved, and should stay that way.
    8. Update `tests/test_lambda_function.py` / `tests/test_stream_lambda_handler.py` to cover both the Secrets-Manager-fetch path (mocked `boto3` client) and the env-var fallback.
  - **Side benefit**: because the fetch happens in `_after_restore` rather than being baked into deploy-time config, rotating the QA/Prod Secrets Manager secret takes effect the next time *any* execution environment restores from the snapshot — no redeploy required (though not instant: an already-warm, non-restored environment keeps whatever it fetched at its own last restore until it eventually recycles).
